随着原本基于 Hexo 框架 Redefine 主题框架的迁移工作正式完工，即基于 Astro 框架 Firefly 主题的博客部署完成，我的博客模板寻找和源码修改工作也正式完结，可以静下心看看书写写文章了。

虽然我对前端代码一无所知，但仍然选择了需要对前端开发有一定了解的 Astro 框架，是因为希望我能在博客的开发过程中主动接触一些先进的前端知识。回看从 2026 年 4 月 18 日开始的博客部署之旅，经历了诸多困难，绕过了很多技术上的弯路，也在众多方案中选择了如今稳定的这一条技术路线。博客的部署迭代过程可以在 更新动态 中找到完整的记录。

为了纪念本博客顺利部署，也能给后来想要部署博客的人部分参考，减少踩坑的几率，因此写下此文，记录前端小白从更换框架，部署失败到最终加入自定义元素、丰富博客内元素的全过程。以下全部教程均基于部署至 Github Pages 的经验。

来自 DeepSeek 老师的详细对比：

  • 🟢 Hexo：更简单、更安心的“稳妥牌”

    Hexo最大的优势就是上手快，中文资源多。对于没有任何前端经验的你，跟着一篇保姆级教程，最快30分钟就能上线一个能访问的博客，能让你获得极快的正反馈。

    这种 “内容与界面分离” 的经典设计，也让日后更换主题、迁移博客都非常方便，非常适合只想专心写作的人。众多成熟的主题也能让你不用接触太多前端代码，就得到一个不错的博客外观。

  • 🔵 Astro：更现代、更专业的“潜力股”

    Astro是2024-2025年静态博客领域的 “当红炸子鸡”，凭借极致的性能和现代化的设计理念受到越来越多开发者追捧。

    虽然Astro的生态和教程不如Hexo丰富，但它在性能和灵活性上更优。它的 “岛屿架构” 能让你使用 React、Vue 等现代前端框架来构建组件。如果你将来希望拓宽技术栈，这可以成为一个很好的起点。

个人建议：

  • 偏好明确——先跑起来再说：请果断选择 Hexo。这能确保你用极低的成本迅速开启写作，对新手最友好、最无痛。
  • 追求体验——愿意为更好投入：如果你享受技术探索的乐趣，对博客的极致性能和独特设计有追求，不妨直接挑战 Astro。它的前瞻性架构能给你带来惊喜和成就感。

Astro 框架的部署#

前置要求：

  • Node.js v22.12.0 或更高版本: 运行 JavaScript 必备的组件。
  • pnpm 包管理器 : 管理项目依赖的包。
  • git : 管理文件版本以及和 Github 仓库的联动。

若是从零开始部署，详见 安装 Astro。若有喜欢的 Astro 主题，可以参考主题内的 README 文件或主题文档进行部署。

TIP

若是直接选择了自己喜欢的 Astro 主题部署，则文件目录中除了 Astro 官方文档中提及的结构外，还可能会有 .git 和 .github 文件夹。

.github 文件中记录了一些原作者的自动化流程 (workflows 中记录的内容)。建议询问 AI 里面的自动化流程内容是什么，对博客的部署有没有影响，我因为对 Github 自动化工作流不了解，曾在将项目上传至 Github 上时一度收到 Github Action 失败发送来的提醒邮件。后才查明是原作者的自动化工作流让我在每次上传文件的时候自动部署，但由于我的配置还不完善，因此一直部署失败。建议根据 AI 的提示保留和改动。

如果你和我一样，喜欢在项目的客制化上做文章，那么可以参考我的实现方式，或者是你是使用 git 工具的新手，则建议观看此部分内容，否则可以跳过。

由于本站是由 Hexo 框架迁移至 Astro 框架，因此先简单介绍一下二者在部署思维上的差别。

在本地文件夹中部署了项目后，需要使用 git 工具对项目的文件版本进行管理。这一段过程虽然较为繁琐，但有了初始的积累后，后续版本的管理将会变得非常轻松。若不及时管理容易出现两个问题：

  1. 文件版本很难回退，若进行某些代码更改后发现项目出现大量 bug 无法修复，想要回退到进行这次大规模修改前的版本，除非已经对原版本进行过备份，否则很难进行项目文件版本的回退。

  2. 查看自己的修改记录困难，并且难以管理和合并主题开发者的后续更新。使用 git 工具能更方便地查看、拉取源仓库的更新，对自己客制化的项目以及源仓库进行冲突合并。

以下根据个人需求和爱好分成两种管理方式进行详述，分别为代码仓库公开 (public) 的方式，和代码仓库私有 (private) 的方式。

在这个仓库的 main 分支存放博客源码，源码中包含了 Github Actions 的工作流，每当往 main 分支推送更改时，Github Actions 就会自动往仓库的 gh-pages 分支上创建静态网站文件，Github 从 gh-pages 上的这些静态文件来构建你的个人网站。

代码仓库私有的管理方式#

如果你和我一样，想从代码层面更改自己的配置，但又害怕自己代码写的不好或其他原因不想公开源码仓库，那么配置会稍微麻烦一些，需要使用到 SSH 密钥来进行不同仓库之间的推送。

此工作流程的原理为：创建两个仓库，一个私有仓库用于存放你的博客源码，另一个公开仓库用于存档生成的静态文件。假设私有仓库和公开仓库均使用了 main 分支存储 (后续的讨论也基于此)。

私有仓库中包含了源码和 Github Actions 的工作流，当你向私有仓库 main 分支推送更新时， Github Actions 就会跨仓库地自动往公开仓库的 main 分支上创建静态网站文件，Github 从公开仓库 main 上的这些静态文件来构建你的个人网站。

后续与源主题项目的合并#

如果只是部署好了博客，以后只写文章，也无需后续的功能、版本更新或者 Bug 修复，那么到上一步已经算正式部署完成了。但是若想及时获取模板的更新，那么还需要进行一些额外的设置。如果能够熟练使用 Git 工具，则可跳过此段。

Git 工具中有一个非常方便的功能，设置上游仓库。可以根据上游仓库和本仓库的区别 (通过 Git 的版本管理功能实现) 自动高效合并代码。因此项目中的 .git 文件不建议进行删除，所有的基于历史修改合并代码的操作均需要此文件中的记录来实现。

博客自定义域名的绑定#

学过计算机网络的都知道，域名只是一个方便人们记忆的一串字符。真正要获取到服务，还需要将域名转换为 IP 地址，访问 IP 地址的服务器并申请资源进行浏览。因此，如果没有觉得 Github 的默认域名 username.github.io 辨识度不高，或者不嫌弃默认域名的访问速度 (因为只有自定义域名才能享受到加速访问的服务)，可以跳过此段。

自定义域名的申请#

目前仍然有几个免费的域名申请网站，但都需要在到期前及时续期。在腾讯云、阿里云上也有很多按年付费的域名，其中有最简单最便宜的是 “xxxxxx.xyz” 纯数字+xyz域名。具体的申请方式在此 Bilibili 视频 免费域名合集 中有较为详细的讲解。

此处推荐的可申请的免费域名均可托管至 Cloudflare，因为后续还有相关的托管操作。如果无需托管到 Cloudflare，可以从其他免费渠道来申请自定义域名。或者直接购买付费域名，直接使用付费平台的 CDN 加速服务。

TIP

如果是使用国内的平台进行域名购买，一般需要进行网站备案才能进行国内的域名解析和 CDN 加速。注意参考购买网站的说明。

托管至 Cloudflare 加速博客访问#

国内由于 DNS 污染的原因，访问 Github 速度较慢，有时甚至连接不上服务器，因此需要使用一个中转站，将流量通过中转站中离访问者最近的节点代理发送至 Github 服务器，这就是 CDN 加速的原理。由于使用 Cloudflare 对域名进行加速访问，因此也默认使用 Cloudflare 的域名解析服务。
